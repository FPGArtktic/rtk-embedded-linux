# Evaluation: rtk on Yocto and Buildroot

What rtk saves on this workload, where it loses information, where it does not run at all, and what to report
upstream. Measured with **rtk 0.48.0** on the reference design in `examples/rpi`, which builds a Raspberry Pi 4
(64-bit) image twice: once with Poky `yocto-5.0.20` (scarthgap) and meta-raspberrypi, once with Buildroot
`2026.02.3`. Each build ran in rootless Podman 6.1.3 on a 16-core / 62 GB host.

## How the numbers were produced

- **Samples.** Every command was run once through `scripts/capture.sh`, which stores exactly what it printed
  (stdout+stderr, ANSI intact) in `samples/<yocto|buildroot>/<name>.log` and the command plus its exit status
  in `<name>.cmd`. Two logs above 1 MB are trimmed in the repository (see the † mark). Their raw size is the size
  of the original capture, taken from `.cmd`.
- **Replay.** `scripts/measure.sh` runs each sample through the real rtk binary, with a PATH shim that prints the
  sample instead of running the tool and replays its exit status. "Agent sees" counts every byte rtk printed,
  including its own `[full output: …]` / `[see remaining: …]` hint lines.
- **Tokens.** "~Tokens saved" is (raw − shown) / 4, an estimate. Real hook runs, counted by rtk itself
  (`rtk gain`), are in a separate table.
- **Regenerate.** `scripts/update-docs.py` rewrites every generated table in this file and in `README.md`, so the
  two cannot drift apart.

### What the agent would have seen without rtk

Claude Code limits large tool output on its own. In this session a 61.9 KB result was replaced by a 2 KB preview
plus a file path. For a full build without rtk, the agent would therefore not read 177 k (Yocto) or 1.3 M
(Buildroot) tokens. It would read the first 2 KB of the log, which is NOTE progress or wget output, and never the
error at the end. For these commands rtk's real gain is **that the agent sees the error at all**. For mid-size
outputs (5–60 KB: `bitbake -s`, `bitbake-getvar`, `legal-info`, failures) the token numbers above are the actual
saving.

## rtk defects found

Every item below reproduces with rtk 0.48.0. Source references point at tag `v0.48.0`.

1. **A `match_command` without a leading `^` is dropped silently on the hook path.** A filter whose
   `match_command` has a top-level branch that does not start with `^` is removed by `is_fully_anchored`
   (`src/core/toml_filter.rs`). `rtk rewrite`, which the hook calls, drops it **without any message**. Only
   executing `rtk <cmd>` prints a warning. `rtk trust` lists such a filter as active, with "No high-risk patterns
   detected". Patterns like `(?:^|[;&|'"]\s*)tool` therefore look valid and never fire. Workaround: prefix with
   `^.*?`. Repro:
   ```bash
   mkdir -p /tmp/t/.rtk && cd /tmp/t && cat > .rtk/filters.toml <<'EOF'
   schema_version = 1
   [filters.x]
   match_command = "(?:^|;\\s*)zz(?:\\s|$)"
   on_empty = "x"
   EOF
   rtk trust --yes          # "Filters: 1 ... No high-risk patterns detected"
   rtk rewrite 'zz a'       # prints nothing, and no warning
   ```
2. **Filters are tried in name order, not file order.** Filters are deserialised into a `BTreeMap`, so within one
   file the first match is the alphabetically first **name**. The upstream README says only "first match wins",
   which suggests file order. Overlapping filters therefore resolve by name. These filters are mutually exclusive
   by construction, and `scripts/check-routing.py` proves it.
3. **rtk's built-in `docker` handler bypasses TOML filters.** `docker run|exec … bitbake/make` goes to
   `run_docker_passthrough` and is never filtered. This is tracked upstream as
   [#821](https://github.com/rtk-ai/rtk/issues/821). Details, reproduction and workarounds:
   [README → Docker](README.md#docker-why-docker-run--bitbake-is-not-filtered-and-what-to-do-instead).
4. **The tee file keeps the head of the log, not the tail.** On a failing exit code, or when a filter cuts lines,
   rtk saves the raw output to `~/.local/share/rtk/tee/` and prints its path. The file is cut at
   `[tee] max_file_size` (default 1 MiB) **from the end**, so it keeps the first MiB. A build log puts its
   failure last, so for a full Buildroot build (5.4 MB) the saved file does not contain the error the hint
   points to. Suggestion: keep the tail, or head + tail, when truncating.
5. **The built-in `make` filter hides Buildroot failures.** `src/filters/make.toml` drops every `^make\[\d+\]:`
   line and keeps the **first** 50 lines. On a failed Buildroot package build it removes
   `make[1]: *** [package/pkg-generic.mk:273: …/rtk-fail-compile-1.0/.stamp_built] Error 1`, which is the only
   line that names the failing package and step. On a long build it is worse. Replaying
   `buildroot-make-fail-compile-long.log` (`make linux-rebuild rtk-fail-compile`, 5 783 lines, exit 2) through
   the built-in filter shows 52 lines of kernel-module install progress, **no `error:` and no `make: ***`**. The
   error survives only in the tee file, and only because that log (541 KB) is under the 1 MiB tee cap
   (defect 4). To reproduce, replay the sample from a directory without `.rtk/`. This project's `buildroot-*`
   filters exist partly to keep that filter away from Buildroot.
6. **`head -N file` is rewritten to `rtk read file --max-lines N`, which shows about N/2 lines.**
   `head -4 samples/buildroot/buildroot-show-targets-list-defconfigs.log` prints 2 lines and `[308 more lines]`,
   and `--max-lines 10` prints 5. A command that asks for N lines should get N.
7. **`filter_stderr = true` appends stderr after stdout.** stdout and stderr are captured separately and
   concatenated (`format!("{}{}", stdout, stderr)` in `run_fallback`), so their interleaving is lost. With
   BitBake this would print each ERROR after the task log it introduces. `bitbake-build` therefore keeps
   `filter_stderr = false`. Buildroot needs `true`, because wget progress and compiler noise go to stderr.
8. **rtk buffers the whole output.** The TOML path uses `Command::output()`, so nothing is shown until the
   command exits. A two-hour Yocto build prints nothing for two hours. For an agent that waits anyway this is
   harmless. For a human watching it is surprising.

## Where rtk does not run at all

rtk only filters a command that the hook rewrites. With 0.48.0 it does not rewrite:

- **Pipelines.** Only the last stage is ever rewritten, so `bitbake X 2>&1 | tail -50` and
  `bitbake -e X | grep ^S=` reach the agent unfiltered. That is the right call for a producer whose output the
  agent explicitly post-processes, but it means the common `| tail` habit gets nothing from these filters.
- **A compound command containing `$(…)`, backticks, or a file redirect in any segment** is not rewritten at
  all, not even its other segments. `bitbake X >/dev/null 2>&1` (redirect in the same segment) is fine.
- **`bash -c '…'`** at the top level.
- **`docker …`** (defect 3).

## Lossy cases

These are the cases where the agent would have to do something extra to get what it needs. None of them
requires re-running a build.

1. **`bitbake -e`: variable history.** The `# $VAR [N operations]` comments are dropped, and they are not in
   rtk's tee file either, because the tee keeps the filtered text. *Instead:*
   `bitbake-getvar -r <recipe> VAR`, whose filter keeps every operation with file:line. Or
   `bitbake -e X | grep -B30 '^VAR='`: a pipeline, which rtk never filters.
2. **`bitbake -e`: everything after line 100.** It is in the tee file named in the hint
   (`tail -n +101 <file>`, or `grep '^VAR=' <file>`). This holds as long as the comment-free environment stays
   under rtk's tee cap (1 MiB by default; 1 018 416 B here). A bigger recipe loses the end of the file, which
   holds the function bodies. *Remedy:* raise `[tee] max_file_size` in `~/.config/rtk/config.toml`.
3. **Buildroot clean build: upstream compiler and configure warnings.** A successful build becomes
   `buildroot: OK`. The tee file holds the first 1 MiB of the raw log only (defect 4). *Instead:*
   `make <pkg>-rebuild 2>&1 | grep -i warning` for the package in question (a pipeline, unfiltered). Buildroot's
   own `WARNING:` lines, `make: ***`, `error:`, `undefined reference` and `No rule to make target` turn off
   the one-line verdict, so they are always shown.
4. **Buildroot failure: only the last 200 filtered lines.** A failing `make` stops at the error, which is
   therefore last. In the long-failure sample (5 783 raw lines), 15 filtered lines remained. A top-level parallel build that keeps
   printing after the error could push the error out of the 200 lines. This was not observed. The tee file
   then has the raw log up to 1 MiB.
5. **`make legal-info`: ERROR placement (live runs only).** See the table. The ERROR lines themselves are
   kept.
6. **`bitbake-getvar`: `[doc]` text, varflag operations and the unexpanded value.** These are the same for every
   recipe, or duplicate the final value.
7. **`bitbake <target>`: the Build Configuration block** (`MACHINE`, `DISTRO`, layer revisions) is dropped.
   *Instead:* `bitbake-getvar MACHINE`.
8. **rtk's own lossy behaviour, independent of these filters:** `head -N file` shows about N/2 lines
   (defect 6). The built-in `make` filter applies to any `make` these filters do not claim (defect 5).

## Verdict

**Deploy it for Yocto and Buildroot work, with these filters and three caveats.**

- **The expensive outputs shrink the most, and nothing important is lost.** A full Yocto build goes from
  946 742 to 496 bytes (99.94%). `bitbake -e` goes from 2.17 MB to the first 100 lines plus a greppable file
  (99.77%). A full Buildroot build goes from 5.36 MB to one line (99.99%). In every failure sample the
  filtered output still names the failing recipe or package, the task or step, the error and the log path.
  Over all 23 samples the reduction is 98.56%. Over 21 real hook runs, rtk counted 96.74%. The mid-size
  commands (`bitbake -s`, `getvar`, `legal-info`, listings) gain 19–76%. The passthrough rows gain nothing,
  which is by design.
- **Runtimes.** Tested end to end through the hook: host-style commands inside `scripts/ctr.sh` with rootless
  Podman 6.1.3, Docker 29.9.0 and Apptainer 1.5.4, plus direct `apptainer run …` (all on rtk 0.48.0). Direct
  `podman run|exec …` is covered by `rtk rewrite` and `RTK_TOML_DEBUG` checks. Singularity is not tested.
  **Docker works only through a `*.sh` wrapper** (defect 3).
- **Caveat 1: rtk sees only plain commands.** Pipelines (`| tail`, `| grep`), compound commands containing
  `$(…)`, backticks or a file redirect, and `bash -c '…'` are never filtered. An agent that habitually runs
  `bitbake X 2>&1 | tail -50` gets nothing from rtk. It should be told to run the bare command.
- **Caveat 2: recovery is weaker than it looks.** The tee file is cut to the first 1 MiB (defect 4), so for a
  full-build log the `[full output: …]` hint does not lead to the end of the log. The filters are therefore
  written so that the error itself is always in the filtered output, and they do not rely on the tee.
- **Caveat 3: trust after every edit.** rtk records trust as a hash of the filter file. After any change,
  `rtk trust` must be run again, or the filters are skipped **silently**.

Pin **rtk ≥ 0.48.0**. That is the version all of the above was measured with, and the `^`-anchoring rule
(defect 1) that the filters rely on exists in it.
